# LLM-as-Judge Evaluation Pipeline

An automated, structured evaluation pipeline for scoring and comparing LLM outputs using an LLM as a judge. It features robust structured output parsing (via Pydantic), pairwise A/B comparison with position bias mitigation, and validation suites to detect sycophancy and verbosity bias.

## Architecture

```text
    +-----------------+      +-----------------+      +------------------+
    |   Test Suite    |      |  Config (YAML)  |      |   LLM Judge      |
    | (JSON/YAML)     |      +--------+--------+      | (OpenAI/Gemini)  |
    +--------+--------+               |               +--------+---------+
             |                        |                        |
             v                        v                        v
    +--------------------------------------------------------------------+
    |                          Evaluator Orchestrator                    |
    |                                                                    |
    |  1. Parse Test Cases (Pydantic Models)                             |
    |  2. Construct Pairwise Prompts (A vs B, B vs A)                    |
    |  3. Enforce Structured Verdict (Criteria, Reasoning, Score)        |
    |  4. Detect Position Bias & Aggregate Results                       |
    +---------------------------------+----------------------------------+
                                      |
                                      v
                             +--------+--------+
                             |     Metrics     |
                             |   (JSON Logs)   |
                             +-----------------+
```

## Setup Instructions

1. **Install dependencies**:
   Ensure you have Python 3.10+ installed.
   ```bash
   pip install -r requirements.txt
   ```

2. **Configure Environment variables**:
   Copy `.env.example` to `.env` and fill in your API keys.
   ```bash
   cp .env.example .env
   # Edit .env and add OPENAI_API_KEY and/or GEMINI_API_KEY
   ```

3. **Configure the pipeline**:
   Edit `configs/config.yaml` to select your preferred judge provider (`openai` or `gemini`) and model name. Note: To prevent self-enhancement bias, it's recommended to use a judge model from a different family than your generators (e.g., use OpenAI to judge Gemini models).

## Usage

### Run a Standard Evaluation

Evaluate a test suite of inputs and model outputs:
```bash
python eval/run_eval.py
```
This will parse the test suite defined in the config, run the A/B evaluation, and output a detailed metrics report in `results/metrics.json` including the win rate and flip rate.

### Run Judge Validation

Validate the judge against an adversarial test suite to check for sycophancy and verbosity bias, and compute the agreement rate (Cohen's Kappa):
```bash
python eval/validate_judge.py
```

## Discussion & Bias Mitigation

### Position Bias
**Problem**: The judge may arbitrarily favor the model presented first (or last).
**Mitigation**: For every test case, the pipeline evaluates `Model A vs Model B` and `Model B vs Model A`. A win is only recorded if the judge consistently chooses the same model. The proportion of cases where the judge changes its mind based on order is reported as the **Position Bias Flip Rate**.

### Verbosity & Length Bias
**Problem**: Judges often favor longer, more verbose responses even if they contain no extra value.
**Mitigation**: The rubric explicitly instructs the judge to penalize unsupported length or fluff. The `validate_judge.py` script tests this using the adversarial suite, ensuring the judge is not tricked by padded answers.

### Sycophancy / Style Bias
**Problem**: Judges can be fooled by confidently wrong, polite, or highly formatted responses.
**Mitigation**: The structured output forces the judge to write step-by-step reasoning for *each specific criterion* (Correctness, Faithfulness, etc.) before assigning a final score or choosing a winner. The adversarial suite contains a sycophancy test (where the model politely agrees with a mathematically incorrect user premise) to ensure the judge correctly identifies factual errors over politeness.

### Self-Enhancement Bias
**Problem**: Models tend to prefer outputs generated by models from their own family.
**Mitigation**: The architecture supports swappable LLM clients via an abstract interface (`LLMClient`), making it trivial to configure a judge from a different family (e.g., use `gpt-4o` to judge outputs from `gemini` models).
